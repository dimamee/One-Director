## 0. Контекст (прочитай перед работой)

**Проект:** One Director — система скрининга сговора (картелей) на госзакупках Узбекистана.
**Хакатон:** Competition & Consumer Protection AI Challenge 2026, задача AI-10 «Выявление сговора на торгах». Даты: 2–4 декабря 2026, 48 часов, техническое жюри Комитета по конкуренции.
**Команда:** Rigged? (3 человека, код пишут ИИ-агенты, люди проверяют).

**Что делает система:**
1. Собирает открытые данные с площадки etender.uzex.uz: сделки, лоты, участники с ИНН.
2. Считает признаки сговора: скидку от стартовой цены, число участников, соучастие, ротацию победителей, «вечных вторых», общих учредителей/директоров/адреса.
3. Строит граф связей фирм и людей (networkx).
4. Даёт риск 0–100 по лоту и фирме: правила + Isolation Forest, объяснение SHAP.
5. LLM пишет справку по лоту на узбекском и русском со ссылкой на ст. 19 ч. 2 и ст. 29 Закона ЗРУ-850 «О конкуренции».
6. Дашборд: очередь рисков, карточка лота, граф, карта регионов, экспорт PDF.

**Ключевой принцип:** флаг — не обвинение. Система помечает признаки для проверки, решение принимает инспектор комитета.

**Почему безопасность критична:**
- Система работает с данными о реальных компаниях и людях (директора, учредители, ИП) — это персональные данные по Закону РУз ЗРУ-547 «О персональных данных».
- Ошибка или утечка может публично обвинить невиновную фирму.
- Заказчик (комитет) в ТЗ Всемирного банка на аналогичную систему требует: хранение данных в Узбекистане, разграничение доступа по ролям, ежедневные резервные копии, соответствие закону о персональных данных.
- Жюри прямо оценивает слой «Xavfsizlik, maxfiylik va tushuntiriladigan AI» (безопасность, приватность, объяснимость).

## 3. Безопасность — что должно быть заложено (документы в Фазе 0, код в Фазе 1)

### 3.1 Секреты
- Секреты только в переменных окружения / `.env` (в `.gitignore`), шаблон — `.env.example` с пустыми значениями: `ANTHROPIC_API_KEY=`, `APP_SECRET_KEY=`, `PSEUDONYM_SALT=`, `DEMO_MODE=true`, `ALLOWED_ORIGINS=`.
- Загрузка через `pydantic-settings`; приложение не стартует, если обязательный секрет пуст.
- Секреты никогда не попадают в логи, ответы API, исключения, ноутбуки, коммиты.
- Сканирование секретов: `gitleaks` в pre-commit и в CI; `detect-private-key` в pre-commit.
- Раздел в `docs/incident-response.md`: что делать при утечке ключа (отозвать, перевыпустить, вычистить историю, сообщить команде).

### 3.2 Персональные данные (ЗРУ-547 «О персональных данных»)
- **Минимизация:** храним только поля, нужные для признаков. Паспортные данные, личные телефоны, домашние адреса физлиц не собираем.
- **Псевдонимизация людей:** ФИО директоров/учредителей → `person_id = HMAC-SHA256(PSEUDONYM_SALT, нормализованное ФИО)`. Совпадения находятся по хешу, ФИО в открытом виде в БД не хранится.
- **ИНН и имена ИП и физлиц** маскируются везде, кроме роли с явным доступом; в `DEMO_MODE` — всегда («ИП ***», «ООО А/Б/В»).
- Адреса и телефоны фирм сравниваются по хешам нормализованных значений.
- **Локализация:** для пилота данные хранятся на серверах в Узбекистане (требование закона и ТЗ комитета); в README указать, что демо на хакатоне — локальное.
- **Сроки хранения:** сырые выгрузки удаляются после обработки; в `docs/data-protection.md` описать политику.
- **Внешние сервисы:** в LLM и любые облачные API уходят только агрегированные факты лота без персональных данных.
- В `docs/data-protection.md`: таблица «какие данные → откуда → класс → где хранятся → кто видит → сколько хранятся». Пометка: точные статьи закона проверить по lex.uz.

### 3.3 Этика и безопасность сбора данных (`docs/scraping-policy.md`)
- Только публичные эндпоинты без авторизации, не чаще 1 запроса в секунду, экспоненциальная задержка при ошибках, остановка при 429/403.
- Понятный User-Agent с контактом команды.
- TLS-проверка включена, таймауты на каждый запрос, ограничение размера ответа.
- Никакой массовой загрузки документов и договоров.
- Ответы API валидируются pydantic-моделями; неожиданные поля логируются, но не ломают пайплайн.
- Реестр юрлиц — только точечно, для фирм из флагнутых лотов.

### 3.4 Безопасность LLM (`docs/llm-safety.md`)
- **Prompt injection:** названия лотов, описания, имена фирм — недоверенный ввод (кто угодно может создать лот с текстом «игнорируй инструкции»). Передавать в LLM только структурированные поля в JSON, внутри явных разделителей, с системной инструкцией считать их данными.
- LLM не получает инструментов, доступа к сети и к БД.
- **Валидация вывода:** ответ — строгий JSON по pydantic-схеме; отклонять, если в справке есть суммы, ИНН или названия, которых нет во входе; отклонять слова «нарушение доказано», «картель» о конкретной фирме.
- Ссылки на статьи закона берутся из фиксированного справочника, а не генерируются.
- Температура 0, таймаут, лимит токенов и бюджет на сессию.
- Промпты и ответы логируются без персональных данных.
- Кэш справок для демо-лотов (работа без интернета).
- Рядом со справкой инспектор всегда видит исходные цифры.

### 3.5 Аутентификация и разграничение доступа (`docs/access-control.md`)
- Роли: `viewer` (только очередь с маскированием), `analyst` (карточки, граф, справки), `supervisor` (+ снятие маски, экспорт), `admin` (пользователи).
- Токены: короткоживущий JWT (15–60 мин), подпись `APP_SECRET_KEY`; пароли, если есть, — argon2.
- Принцип наименьших привилегий; проверка роли на каждом эндпоинте на сервере, не только в интерфейсе.
- Матрица «роль × эндпоинт × действие».

### 3.6 Безопасность API и веба
- Валидация всех входных параметров (pydantic): типы, длины, диапазоны, белые списки для сортировки и фильтров.
- **SQL:** только параметризованные запросы DuckDB, никакой склейки строк.
- Пагинация с максимальным размером страницы; лимит запросов (rate limiting) на пользователя и IP.
- CORS только для `ALLOWED_ORIGINS`; заголовки безопасности (CSP, X-Content-Type-Options, X-Frame-Options, Referrer-Policy, HSTS при HTTPS).
- Ошибки без стек-трейсов и деталей реализации; `debug=False` вне локальной разработки.
- Защита от path traversal при отдаче PDF; имена файлов генерируются сервером.
- Фронт: экранирование всех строк из данных (названия фирм могут содержать HTML/JS); в Streamlit не использовать `unsafe_allow_html=True` с данными; в pyvis экранировать подписи узлов.
- PDF: экранировать содержимое, без внешних ресурсов.

### 3.7 Аудит и логи
- `audit_log`: кто, когда, какую фирму/лот открыл, снял маску, выгрузил PDF. Только добавление записей, без изменения.
- Структурированные логи (JSON) с фильтром, вырезающим секреты и персональные данные.
- IP в логах — в виде хеша.

### 3.8 Цепочка поставок и код
- Версии зафиксированы (`pip-compile`, по возможности `--generate-hashes`).
- `pip-audit` в CI; Dependabot для pip и GitHub Actions.

- CI (`.github/workflows/ci.yml`): ruff → mypy → bandit → pip-audit → gitleaks → pytest. Права workflow минимальные (`permissions: contents: read`), версии actions зафиксированы.
- Защита ветки main: merge только через PR с зелёным CI (описать в README как настроить).

### 3.9 Контейнер и развёртывание
- Dockerfile: slim-образ с фиксированным тегом, multi-stage, запуск от непривилегированного пользователя, без секретов в образе, `HEALTHCHECK`.
- docker-compose: файловая система только для чтения где возможно, `no-new-privileges`, лимиты памяти/CPU, порт только на localhost по умолчанию.
- `.dockerignore`: `.env`, `data/`, `.git`, ноутбуки.
- Ежедневный бэкап БД (описать в README для пилота).

### 3.10 Безопасность модели и решений
- `docs/model-card.md`: назначение, данные, признаки, метрики, ограничения, известные риски ложных срабатываний, человек в контуре.
- Пороги и веса продакшн-режима задаются через конфигурацию/окружение, не захардкожены в публичном коде (чтобы картель не подстроился под опубликованные пороги).
- Каждый флаг хранит `evidence` — воспроизводимые факты, на которых он основан.
- Версия модели в каждом `risk_score`.
- Метрики на синтетике и на реальных делах не смешиваются.

**Заглушки тестов безопасности** в `tests/security/` (в Фазе 0 — `pytest.mark.skip` с описанием, в Фазе 1 — реализовать):
- секреты не попадают в логи и ответы;
- в `DEMO_MODE` нет немаскированных ИНН/ФИО физлиц и ИП ни в одном ответе API;
- SQL-инъекция в параметрах фильтров не проходит;
- XSS-строка в названии фирмы экранируется в дашборде и PDF;
- prompt injection в названии лота не меняет формат и смысл справки;
- эндпоинты без токена → 401, с недостаточной ролью → 403;
- rate limiting срабатывает;
- path traversal в `/reports/` не проходит.

### 3.14 docs/threat-model.md
Модель угроз по STRIDE: активы (данные о фирмах и людях, ключи, модель, справки), участники (инспектор, админ, внешний злоумышленник, фирма-картель, сам LLM), угрозы и меры. Обязательно разобрать:
- утечка персональных данных;
- ложное обвинение фирмы (ошибка модели или подмена справки);
- prompt injection через данные лотов;
- подстройка картеля под опубликованные пороги;
- отравление данных (фиктивные лоты);
- компрометация ключа API;
- вредоносная зависимость;
- блокировка нашего сборщика площадкой / нарушение её условий.

## 4. Фаза 1 — только после разрешения оргкомитета

Реализовать модуль `src/one_director/security/` и снять skip с тестов безопасности:
1. `settings.py` — загрузка конфигурации и секретов через pydantic-settings, падение при пустых обязательных значениях.
2. `pseudonymize.py` — HMAC-псевдонимы для людей, нормализация ФИО (латиница/кириллица), хеши адресов и телефонов.
3. `masking.py` — маскирование ИНН/имён ИП и физлиц по роли и `DEMO_MODE`.
4. `logging.py` — JSON-логи с фильтром секретов и персональных данных.
5. `http_client.py` — httpx-клиент: лимит 1 запрос/с, ретраи с backoff, таймауты, TLS, ограничение размера ответа, понятный User-Agent.
6. `llm_guard.py` — подготовка безопасного промпта и валидация ответа LLM (раздел 3.4).
7. `auth.py` — JWT, роли, зависимость FastAPI для проверки роли.
8. `audit.py` — запись в audit_log.
