# Защита данных и персональные данные

Версия 0.1 (Фаза 0). Основание: Закон РУз ЗРУ-547 «О персональных данных» (2019) с изменениями, ТЗ комитета (хранение в Узбекистане, разграничение доступа, ежедневные бэкапы).

> **Пометка.** Точные номера статей и формулировки закона (в т. ч. требование о локализации баз данных граждан РУз, порядок уведомления об утечке, роль уполномоченного органа) **проверить по lex.uz** до пилота. Ниже ссылки даны как ориентир, а не как юридическое заключение.

## 1. Принципы

1. **Минимизация.** Храним только поля, нужные для признаков сговора (`specs/schema.md`). Не собираем: паспортные данные, ПИНФЛ (JShShIR) физлиц, личные телефоны, домашние адреса физлиц, e-mail, даты рождения, фото, документы и договоры целиком.
2. **Псевдонимизация людей.** ФИО директоров и учредителей не хранятся: только `person_id`.
3. **Маскирование по умолчанию.** ИНН и имена ИП и физлиц скрыты везде, кроме роли с явным доступом; в `DEMO_MODE` скрыто всё.
4. **Ограничение цели.** Данные используются только для скрининга признаков сговора и не передаются третьим лицам, кроме комитета в рамках пилота.
5. **Локализация.** Пилот — серверы в Узбекистане. Демо на хакатоне — локально на ноутбуке команды, без облачных хранилищ.
6. **Внешние сервисы получают только агрегированные факты** без персональных данных и без ИНН.
7. **Сроки хранения** определены заранее и выполняются автоматически.

## 2. Классы данных

| Класс | Что это | Правила |
|---|---|---|
| `public` | открыто опубликовано площадкой или госорганом, не относится к физлицу (лот, заказчик-госорган, юрлицо-участник) | можно показывать `analyst`+; в `DEMO_MODE` названия фирм всё равно заменяются алиасами |
| `personal` | относится к физлицу или ИП, включая псевдонимы и хеши (псевдонимизированные данные остаются ПДн) | маскирование, доступ по роли, аудит, не уходит во внешние API |
| `sensitive` | может навредить при утечке: флаги, риск-скоры, справки, evidence, пороги модели, `audit_log` | доступ по роли, не публикуется, пороги — вне репозитория |
| `secret` | ключи и хеши паролей | только переменные окружения / менеджер секретов, никогда в логах, git, образах |

## 3. Реестр обработки: какие данные → откуда → класс → где → кто видит → сколько хранятся

| Данные | Откуда | Класс | Где хранятся | Кто видит | Срок хранения |
|---|---|---|---|---|---|
| Сырые ответы площадки (JSON) | etender.uzex.uz, публичные эндпоинты | public + personal (ИП) | `data/raw/` (локально / сервер в РУз) | никто через UI; только процесс сбора | удаляются после успешной обработки, не позже 7 дней |
| Лоты (`lots`) | etender | public; `title` — недоверенный текст | `data/processed/` (Parquet, DuckDB) | `viewer` — агрегаты; `analyst`+ — карточки | срок пилота + 1 год, затем удаление/архив по решению комитета |
| Заявки (`bids`): ИНН и имя участника | etender | public (юрлицо) / **personal** (ИП) | `data/processed/` | юрлица — `analyst`+; ИП — маска, снятие только `supervisor` с аудитом | как лоты |
| Фирмы (`firms`): тип, дата регистрации | реестр, только флагнутые фирмы | public / personal (ИП) | `data/processed/` | `analyst`+ | как лоты |
| Хеши адресов и телефонов фирм | реестр → HMAC в памяти | personal (псевдоним) | `data/processed/` | не показываются, только факт совпадения | как лоты |
| Псевдонимы людей (`person_id`), роль | реестр → HMAC в памяти | personal (псевдоним) | `data/processed/` | `analyst`+ видят только «общий директор P-3f2a…» | как лоты |
| ФИО директоров/учредителей | реестр | personal | **не хранятся**; существуют только в памяти процесса до вычисления HMAC | никто | 0 |
| Флаги, evidence, риск-скоры | вычисляются | sensitive | `data/processed/` | `viewer` — очередь; `analyst`+ — детали | как лоты; при смене модели старые версии хранятся для воспроизводимости |
| Справки LLM (кэш) | Anthropic API по агрегированным фактам | sensitive | `data/processed/` (`briefs`) | `analyst`+ | как лоты |
| Факты, отправленные в LLM | вычисляются | sensitive, без ПДн | Anthropic API (за пределами РУз); у нас — лог промпта без ПДн | — | по политике Anthropic; у нас — 90 дней в логах |
| Учётные записи (`users`): логин, роль, argon2-хеш | админ | secret (хеш) / personal (логин) | `data/processed/` или файл вне репозитория | `admin` | до удаления учётки + 1 год в аудите |
| `audit_log` | API | sensitive; `object_id` может быть ИНН ИП | `data/processed/` (append-only) | `admin`, по запросу комитета | не менее 1 года (уточнить требование комитета) |
| Технические логи | API, сборщик | sensitive, ПДн вырезаются фильтром | stdout контейнера → ротация (10 МБ × 3) / журнал сервера | команда эксплуатации | 30 дней (демо — до конца хакатона) |
| Бэкапы | ежедневный снимок `data/processed/` | как исходные | зашифрованный архив, второй носитель в РУз | команда эксплуатации | 7 ежедневных, 4 еженедельных, 3 ежемесячных |

## 4. Псевдонимизация

- `person_id = HMAC-SHA256(PSEUDONYM_SALT, "person:" + normalize_name(ФИО))`, hex.
- **Нормализация** (`security/pseudonymize.py`): Unicode NFKC, нижний регистр, единая латинская транслитерация узбекской и русской кириллицы (ш/ч/ў/ғ/қ/ҳ, варианты апострофа `ʻ ’ '`), удаление знаков препинания и лишних пробелов, сортировка токенов имени.
- Адреса и телефоны — тот же HMAC с префиксами `addr:` / `phone:` (телефон в формате E.164). IP в логах и аудите — префикс `ip:`.
- **`PSEUDONYM_SALT` — это секретный ключ**, а не соль: ФИО имеют низкую энтропию, и при утечке ключа их можно восстановить перебором по словарю. Ключ хранится отдельно от данных и бэкапов.
- **Ротация ключа** меняет все псевдонимы. Поскольку ФИО не хранятся, после ротации граф людей пересобирается повторным точечным запросом реестра для флагнутых фирм. Плановая ротация — только между пилотными периодами.
- **Ограничение:** совпадение `person_id` означает совпадение нормализованного ФИО, а не то, что это один человек (однофамильцы). Признак «общий директор» по одному лишь имени — слабый и так помечается в evidence.

## 5. Маскирование

| Объект | `viewer` | `analyst` | `supervisor` | `DEMO_MODE` (все роли) |
|---|---|---|---|---|
| ИНН юрлица | маска | открыто | открыто | маска |
| Название юрлица | алиас («Участник A») | открыто | открыто | алиас «ООО «А»», «ООО «Б»»… |
| ИНН и имя ИП / физлица | маска | маска («ИП ***») | маска; снятие по запросу с причиной → аудит | маска, снятие невозможно |
| Тип лица неизвестен | как ИП | как ИП | как ИП | маска |
| `person_id` | не показывается | короткий префикс `P-3f2a` | короткий префикс | короткий префикс |
| Хеши адресов/телефонов | не показываются | только факт совпадения | только факт совпадения | только факт совпадения |

Маскирование выполняется на сервере в одном месте (`security/masking.py`) до сериализации ответа. Ошибка или неизвестное значение → маска (fail closed).

## 6. Передача во внешние сервисы

- **LLM (Anthropic API):** только агрегированные факты лота — категория, регион, суммы, скидка, число участников, коды признаков, плейсхолдеры участников (`P1`, `P2`). Без ИНН, названий фирм, ФИО, псевдонимов, адресов. Подробно — `docs/llm-safety.md`. Обработка происходит за пределами РУз, поэтому отправка ПДн туда запрещена.
- **Никаких** облачных хранилищ, трекеров, аналитики, CDN для данных. Streamlit: `browser.gatherUsageStats=false`.
- **GitHub:** только код и обезличенные фикстуры (`tests/fixtures/README.md`).

## 7. Логи

- JSON-логи через фильтр (`security/logging.py`): вырезаются секреты, JWT, 9-значные ИНН, 14-значные ПИНФЛ, e-mail, телефоны; IP → `ip_hash`.
- Access log uvicorn отключён (в путях есть ИНН); запросы логирует middleware с маской пути.
- `print()` запрещён правилом ruff `T20`.
- Промпты и ответы LLM логируются без ПДн (их там нет по построению) и проходят тот же фильтр.

## 8. Права субъектов и запросы

- Фирма или человек может запросить сведения о своих данных и исправление ошибок. Канал — через комитет (оператор пилота). Срок ответа — уточнить по ЗРУ-547.
- Исправление ошибочных данных → перерасчёт флагов и скоров с новой версией и записью в аудит.

## 9. Утечка персональных данных

Процедура — `docs/incident-response.md`, раздел «Утечка персональных данных». Порядок и сроки уведомления уполномоченного органа и субъектов — **проверить по lex.uz** до пилота.

- Владелец данных пилота — комитет (оператор). Команда — обработчик по поручению (уточнить договором).
- Ответственный за защиту данных в команде — назначить (открытый вопрос).
