# Реагирование на инциденты

Версия 0.1 (Фаза 0). Короткие чек-листы на случай, когда что-то пошло не так. Во время хакатона действуем по ним, не импровизируя.

## 1. Роли

| Роль | Кто | Задача |
|---|---|---|
| Координатор инцидента | ответственный за безопасность (назначить) | принимает решения, ведёт журнал |
| Исполнитель | любой участник команды | выполняет шаги чек-листа |
| Связь | капитан команды | общение с организаторами, комитетом, площадкой |

Журнал инцидента: время (UTC+5), что обнаружено, кто, какие действия, результат. Без ПДн и без значений секретов.

## 2. Уровни критичности

| Уровень | Примеры | Реакция |
|---|---|---|
| **P1 — критический** | утечка ПДн, утечка `PSEUDONYM_SALT` или ключа API, публикация ложного обвинения, компрометация репозитория | немедленно, все дела откладываются |
| **P2 — высокий** | обход маскирования без подтверждённой утечки, уязвимость в API, блокировка сборщика площадкой | в течение часа |
| **P3 — средний** | уязвимая зависимость без эксплуатации, ошибка в справке без распространения | в течение дня |

## 3. Утечка ключа / секрета

Признаки: gitleaks/GitHub push protection сработал, ключ виден в логе, скриншоте, ноутбуке, чате; неожиданные расходы в консоли Anthropic.

1. **Отозвать** скомпрометированный ключ *сразу*, до любых разборов:
   - `ANTHROPIC_API_KEY` — удалить ключ в консоли Anthropic (API Keys), проверить usage/расходы за период;
   - `APP_SECRET_KEY` — заменить значение и перезапустить API: все выданные JWT станут недействительны, пользователи войдут заново;
   - `PSEUDONYM_SALT` — см. п. 4 (особый случай);
   - пароли учёток — сменить, заблокировать затронутые аккаунты.
2. **Перевыпустить** новый ключ и подставить его только в окружение запуска (вне папки проекта). Демо-ключи и пилотные ключи — разные.
3. **Вычистить историю**, если секрет попал в git:
   - помнить: переписывание истории **не отменяет утечку** — ключ уже считается скомпрометированным, отзыв (шаг 1) обязателен;
   - удалить из истории (`git filter-repo --replace-text` или BFG), force-push выполняет человек-владелец репозитория вручную (агентам `git push --force` запрещён), все участники заново клонируют репозиторий;
   - попросить GitHub Support очистить кэшированные представления, если репозиторий публичный;
   - удалить секрет из CI-логов, артефактов, образов Docker (пересобрать и удалить старые теги).
4. **Сообщить команде** в общем канале: какой ключ, когда отозван, что нужно сделать каждому (обновить env, переклонировать).
5. **Найти причину** и закрыть её: добавить правило в gitleaks/фильтр логов, тест в `tests/security/`.
6. Запись в журнал инцидента.

## 4. Утечка `PSEUDONYM_SALT` (P1)

Это ключ псевдонимизации: с ним по словарю ФИО можно восстановить имена людей из `person_id`.

1. Считать все `person_id`, хеши адресов, телефонов и IP **потенциально деанонимизируемыми**.
2. Сгенерировать новый ключ; удалить таблицы `persons` и производные поля в `firms`, граф людей.
3. Пересобрать псевдонимы повторным точечным запросом реестра для флагнутых фирм (ФИО не хранятся — восстановить из нашей БД нельзя).
4. Если вместе с ключом утекли данные (`data/processed/` или бэкап) — это ещё и утечка ПДн, п. 5.

## 5. Утечка персональных данных (P1)

1. Остановить источник: отключить эндпоинт/сервис, отозвать доступы, включить `DEMO_MODE=true`.
2. Определить объём: какие таблицы/поля, сколько субъектов, период, кто получил доступ (по `audit_log`).
3. Сохранить доказательства (логи, аудит) без копирования самих ПДн.
4. Уведомить владельца данных (комитет) немедленно.
5. Уведомить уполномоченный орган и субъектов в порядке и сроки ЗРУ-547 — **порядок и сроки проверить по lex.uz** заранее и вписать сюда до пилота.
6. Исправить причину, добавить регрессионный тест, провести разбор.

## 6. Ложный флаг или подмена справки стали публичными (P1)

1. Отозвать/снять материал там, где он опубликован командой (презентация, скриншот, PDF).
2. Проверить evidence и версию модели: ошибка данных, модели, LLM или подмена?
3. Сообщить комитету и, через комитет, затронутой фирме: «система показала признаки для проверки, нарушение не установлено».
4. Исправить: данные → перерасчёт; модель → новая версия; LLM → правило валидатора; подмена → расследование по `audit_log` и хешу PDF.
5. Обновить `docs/model-card.md` (раздел «Известные ошибки»).

## 7. Prompt injection / некорректная справка (P2–P3)

1. Включить для лота шаблонную справку; сохранить вход (факты) и отклонённый ответ.
2. Добавить payload в `tests/security/test_prompt_injection.py` и правило в `llm_guard`.

## 8. Блокировка сборщика площадкой (P2)

1. Сборщик сам останавливается на 429/403; не перезапускать.
2. Зафиксировать время, ответ сервера, частоту запросов (`docs/scraping-policy.md`, раздел 8).
3. Связаться с площадкой/организаторами; работать на собранных данных.

## 9. Вредоносная или уязвимая зависимость (P1–P3)

1. Заморозить merge; определить затронутые lock-файлы и образы.
2. Откатить/обновить пакет, пересобрать lock с хешами, пересобрать образ.
3. Если пакет выполнялся на машинах команды — считать секреты на этих машинах скомпрометированными (п. 3).

## 10. Компрометация репозитория или учётки GitHub (P1)

1. Сменить пароль, отозвать токены и SSH-ключи, проверить 2FA.
2. Проверить последние коммиты, workflow-файлы, настройки защиты ветки, deploy keys, webhooks.
3. Отозвать все секреты, которые могли быть доступны (п. 3).

## 11. После инцидента

В течение 3 дней (на хакатоне — после демо): короткий разбор без поиска виноватых — что произошло, почему меры не сработали, что меняем (документ, тест, правило). Обновить этот файл и `docs/threat-model.md`.
